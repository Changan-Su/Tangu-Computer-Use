# 探针：第一次读之前窗口被盖住，首读读不读得到网页内容（2026-11-13）

要回答的问题：后台操控的时候用户自己也在用电脑。目标窗口还从没被读过，这时别的 App 抢了前台、或者把它盖住了，第一次读会怎样。

起因：同一天在签名构建上跑 `scripts/web-covered.check.mjs`，有一次 4 轮里 3 轮在按之前就没拿到按钮（首读回来的内容里没有它），几分钟后原样重跑全过。那一次没开采样，原因没有实测；这个探针量的是「有没有一条路能造出同样的结果」。

## 结论

**只抢前台不碍事；首读完成之前被完全盖住，首读就是空壳，盖着期间一直读不到。这是已知问题，还没修。**

| 组别 | 轮数 | 首读有按钮 | 还盖着的 8 秒里自己出现 | 盖窗关掉后出现 |
|---|---|---|---|---|
| control：什么都不抢 | 3 | 3 | — | — |
| front：抢前台，但窗口不压在替身上 | 3 | 3 | — | — |
| coverBefore：抢前台并盖住，页面 hidden 之后才第一次碰它 | 3 | 0 | 0 | 3 |
| coverDuring：第一次碰它之后立刻盖住（落在首读那 2.5 秒等待里） | 3 | 0 | 0 | 3 |

关掉「读之前先问页面」（`PI_COMPUTER_USE_WEB_FLUSH=0`）再量：control 3 / 3；coverBefore、coverDuring 各 0 / 3，盖窗关掉后 3 / 3。结果一样。

- 首读没有按钮的 12 轮，读回来的都只有窗口外壳（16 行，正常是 25 行）。
- 盖窗关掉后每 0.5 秒读一次，12 轮都是第一次再读就有了，落在关掉后 0.70–0.84 秒，所以实际不超过这个数。
- 这不是「先问」带来的，先问也救不了：树里还没有网页区域，没有东西可问。
- 盖窗关掉后，这 12 轮的页面都只可见了 19–102 毫秒就又 hidden 了（盖窗一退出，用户原来停着的窗口又压了上来），之后照样读得到。看起来只要可见过一下树就建起来了，这一句是推断。

对使用的影响：用户自己的窗口完全盖着一扇从没读过的 Electron / 浏览器窗口时，模型第一次读会以为里面什么都没有。已经读到过网页内容之后才被盖住的情形不在这里，那是 `../web-flush/` 量的。

## 怎么量的

脚本 `scripts/first-read-covered.probe.mjs`，走真 `bridge.ts`（`executeFind`、`executeObserve`）和真 helper，只读不按。

- 替身：一个 Electron 窗口，520 × 320，摆在主屏中间，不抢焦点地显示；页面把加载时和每次变化的 `visibilityState` 报回脚本。
- 抢前台的：`vision-fixtures` 的原生盖窗。front 组把它摆在屏幕左上角（不压替身）；两个 cover 组比替身每边大 200 点。
- 每轮：等页面加载完再等 0.8 秒 →（按组别抢前台 / 盖住）→ `find_roots`（第一次接触）→ `observe_ui`（首读，内部等到接触后 2.5 秒再读一次）→ 没有按钮就每 0.5 秒再读，最多 8 秒 → 关掉盖窗，再每 0.5 秒读，最多 6 秒。
- 全程另开采样（每 0.5 秒一行：键鼠空闲秒数、屏幕锁没锁、前台 App）：21 轮期间没有键鼠输入、没有锁屏，前台只在用户原来停着的 App 和盖窗之间来回。

环境：macOS 27.0.1，Electron 40.10.2，helper 是提交 `f06adca` 的签名构建（协议 19）。

## 文件

- `results-ask.json`：先问开着，4 组各 3 轮。
- `results-no-ask.json`：先问关掉，3 组各 3 轮。

每行记了：页面加载时和第一次接触之前的可见性、首读用时和行数、有没有按钮、盖着时 / 盖窗关掉后多久出现、可见性事件的时间线。前台 App 只记「盖窗在不在前台」。

## 没量到的

- 只量了 Electron 40 的一个页面；盖窗只试了「完全盖住」。部分遮挡（页面不进 hidden）没量。
- 盖着超过 8 秒之后会不会自己出现，没量。
- 0.7.1 正式版没有单独量；「关掉先问」是在同一个构建上用开关量的。
- 没试过的修法方向：首读是空壳、进程又是 Chromium 时，对窗口中心也做一次位置查询，看能不能把树催出来。
- 起因里那一次红到底是不是走的这条路，没有数据。
